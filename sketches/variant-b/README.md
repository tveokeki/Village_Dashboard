# Variant B: Unified Revenue Page with Sub-Tabs (หน้ารายรับรวม และสลับด้วยแท็บย่อย)

## การออกแบบ UX/UI
ในการออกแบบนี้ จะมีเมนูหลักเพียงเมนูเดียวบนแถบข้าง (Sidebar) คือ **"จัดการรายรับ" (Revenue)** เพื่อสร้างศูนย์กลางรวมข้อมูลทางการเงินฝั่งขาเข้าไว้ด้วยกันทั้งหมด:
- เมื่อเข้ามาในหน้านี้ ผู้ใช้จะพบกับแถบควบคุมเซกเมนต์ (Segmented Tab Control) ด้านบนอย่างเด่นชัดเพื่อเลือกสลับข้อมูลระหว่าง:
  1. **รายรับค่าส่วนกลาง (Common Fee Revenue):** สำหรับบิลรายเดือนปกติและยอดค้างชำระของแต่ละบ้านเลขที่
  2. **รายรับประเภทอื่น ๆ (Other Revenue):** สำหรับรายการเบ็ดเตล็ด เช่น ดอกเบี้ยธนาคาร, เงินประกัน, ค่าปรับ
- ปุ่มทำงานหลักด้านบน (CTA) จะปรับเปลี่ยนพฤติกรรมไปตามแท็บย่อยที่เปิดอยู่โดยอัตโนมัติ (เช่น บันทึกจ่ายค่าส่วนกลาง หรือ บันทึกดอกเบี้ย/รายรับอื่น ๆ) เพื่อความรวดเร็วในการจัดการข้อมูล

## ข้อดีของ Variant B
- **ประหยัดพื้นที่เมนู (Clean Sidebar):** Sidebar ไม่รก มีหัวข้อการเงินหลักที่เข้าใจง่ายและสอดคล้องกับพฤติกรรมผู้ใช้ทั่วไป
- **เห็นภาพรวมได้รวดเร็ว (Centralized Context):** ผู้ใช้รับรู้ได้ทันทีว่า "ข้อมูลรายรับทั้งหมด" อยู่ภายใต้เมนูนี้ เพียงแค่สลับแท็บเพื่อดูรายละเอียดแต่ละส่วน
- **รองรับ Mobile-First เต็มรูปแบบ:** การใช้แท็บสลับระดับย่อย (Sub-tabs) ด้านบนสอดคล้องกับแนวทางการออกแบบเว็บแอพยุคใหม่ที่แสดงผลบนมือถือได้อย่างเหมาะสม (ไม่เพิ่มจำนวนไอคอนในแถบนำทางด้านล่าง - BottomNav)

## ข้อจำกัดของ Variant B
- **การโหลดหน้าจอหนักขึ้น:** เนื่องจากต้องเตรียมข้อมูลและสถิติ (KPI) ของทั้งสองประเภทในหน้าเดียว หากไม่ได้ใช้ Lazy Loading หรือแยก Client-side State จะส่งผลให้การตอบสนองช้าลงเล็กน้อย (สามารถแก้ได้ด้วยสถาปัตยกรรม Next.js Dynamic Import / API Route Params)

## การแก้ไขปัญหาในส่วนของ Database (เหมือนกัน)
- ปลดล็อกโครงสร้างตาราง `slip_processing.payments` ให้ `member_id` และ `maintenance_fee_id` รองรับค่า `NULL`
- การแก้ไขนี้ทำให้ยอดเงินจาก "ดอกเบี้ยธนาคาร" หรือรายรับอิสระ ไม่เกิดข้อผิดพลาดจาก Foreign Key Constraint
- ในหน้าสเก็ตช์ เมื่อบันทึก "รายรับอื่น ๆ" โดยเว้นค่าสมาชิกไว้ ระบบจะตั้งเป็น `NULL` ทันที ซึ่งทำงานร่วมกับ PostgreSQL ได้อย่างสมบูรณ์แบบ
